# ⚙️ مواصفات Backend — المرحلة 10: محرك النسخ الاحتياطي واستعادة البيانات (Backups Engine)

> **الهدف:** توثيق تفاصيل المعالجة الخلفية، إدارة استعلامات MySQL المباشرة، تقنيات التجزئة الدفعية (Chunking)، ضغط الأرشيفات بـ ZIP، دورة حياة الاستعادة وتعطيل الـ Foreign Keys، وقواعد الصلاحيات (RBAC).

---

## 1. البنية المعمارية للوحدة الخلفية (Backend Module Structure)

```text
backend/src/modules/backup/
├── backup.controller.ts        # معالجة الطلبات، التوثيق، وإرجاع التدفق الثنائي (Stream)
├── backup.service.ts           # محرك تصدير واستعادة MySQL وضغط الملفات
├── dto/
│   ├── create-backup.dto.ts    # التحقق من نص الملاحظة (note)
│   └── upload-backup.dto.ts    # التحقق من معاملات الرفع
└── backup.module.ts            # تسجيل الوحدة وتوفير الخدمات
```

## 2. منطق التصدير والضغط (Export & Compression Mechanism)

### 🔹 خطوات عملية `createBackup(note?: string)`:
1. **تحديد المسارات وتوليد الاسم:**
   - مسار التخزين الافتراضي: `storage/backups/`.
   - اسم الملف القياسي: `backup_YYYY-MM-DD_HH-mm-ss_database.zip`.
2. **تجهيز ملف SQL المؤقت:**
   - كتابة ترويسة النسخة والتوقيت.
   - كتابة أمر التعطيل الصارم: `SET FOREIGN_KEY_CHECKS=0;\n`.
3. **استخراج الجداول وهياكلها:**
   - جلب قائمة الجداول عبر `SHOW TABLES;`.
   - استخراج كود الإنشاء عبر `SHOW CREATE TABLE \`${table}\`;`.
   - كتابة `DROP TABLE IF EXISTS \`${table}\`;` متبوعاً بـ `CREATE TABLE ...;`.
4. **تصدير البيانات بالتجزئة الدفعية (Chunking):**
   - لتفادي تجاوز سعة الذاكرة، يتم عد السجلات `SELECT COUNT(*) FROM \`${table}\``.
   - قراءة السجلات بدفعات بحجم `500` سجل (`LIMIT 500 OFFSET {offset}`).
   - تحويل القيم إلى تمثيل SQL آمن مع الـ Escaping الدقيق والقيم `NULL`.
   - كتابة أوامر `INSERT INTO \`${table}\` (...) VALUES (...);`.
5. **إعادة تفعيل المفاتيح الأجنبية:**
   - كتابة `SET FOREIGN_KEY_CHECKS=1;\n` في نهاية الملف.
6. **الضغط وإضافة الملاحظات:**
   - إنشاء أرشيف ZIP عبر مكتبة `adm-zip` أو `archiver`.
   - إضافة `database.sql` كمدخل رئيسي داخل الأرشيف.
   - في حال وجود ملاحظة نصية (`note`)، يتم إضافتها كملف `note.txt` داخل الأرشيف.
7. **التنظيف والأرشفة:**
   - حفظ ملف الـ ZIP في المسار النهائي وحذف ملف الـ SQL المؤقت.

## 3. منطق الاستعادة الشاملة (Database Restore Mechanism)

### 🔹 خطوات عملية `restoreBackup(filename: string)`:
1. **التحقق من وجود الملف:** التأكد من وجود `storage/backups/${filename}` وإلا رمي استثناء `404 Not Found`.
2. **فك الضغط في مسار مؤقت:**
   - إنشاء مجلد مؤقت `storage/temp_restore_${timestamp}`.
   - فك ضغط الأرشيف والتحقق من وجود `database.sql`.
3. **المحلل الذكي للاستعلامات (Smart SQL Statement Splitter):**
   - قراءة محتوى `database.sql`.
   - تفكيك الاستعلامات بدقة مع مراعاة السلاسل النصية المحتوية على فواصل منقوطة `;` والرموز الخاصة والتعليقات `--`.
4. **التنفيذ المعزول:**
   - تنفيذ `SET FOREIGN_KEY_CHECKS=0;`.
   - تنفيذ كافة أوامر `DROP TABLE` و `CREATE TABLE` و `INSERT INTO` بالترتيب.
   - تنفيذ `SET FOREIGN_KEY_CHECKS=1;`.
5. **التنظيف النهائي:**
   - حذف المجلد والملفات المؤقتة بالكامل.

---

## 4. استعراض وقراءة البيانات الوصفية (Metadata Extraction)

- عند طلب `GET /api/v1/backups`:
  - قراءة كافة ملفات `.zip` في المجلد.
  - استخراج التاريخ من اسم الملف (نمط Regex).
  - فتح الأرشيف للقراءة السريعة والبحث عن `note.txt` دون فك ضغط ملف SQL الكبير.
  - حساب الحجم بالبايت وتنسيقه (KB / MB / GB).
  - الترتيب تنازلياً حسب تاريخ الإنشاء.

---

## 5. الحماية والصلاحيات (Security & RBAC)

- استخدام `JwtAuthGuard` و `RolesGuard`.
- حصر المسارات بـ `@Roles('admin')`.
- حماية مسارات الرفع بفلاتر امتدادات الملفات (`.zip`) والتحقق من الحجم الأقصى (512MB).
